# WPK v8：中断、缺失区域和恢复连续性

日期：2026-09-08。结论：当前范围内的连续性保护、受控故障注入和正常回放回归通过。
生产仍未放行；本轮没有执行真实采集卡拔插，也没有重训或替换权重。

## 新增的连续性保护

`VisionEngine`向支持时序的识别器传递帧号、时间、来源、画布大小和底牌/公共牌ROI及槽位布局。
单帧识别器继续使用原协议；离线记录包装器也转发这项信息，不能在测试时漏掉生产保护。

- 帧号跳跃、重复/倒退，时间倒退或超预算，以及来源/画布/平台布局改变：重新积累全部卡面证据。
- 某组ROI缺失或变更（包括尺寸不变但坐标移动）：只清空该组历史，不误清另一组。
- ROI存在但某个槽位上一帧没有被识别：不能跨过漏调用继续累计旧样本。
- 同一帧反复调用同一个槽位：最多计入一次，不可用重复调用凑足确认帧数。
- 显式标记缺失的ROI不能通过手动调用重新积累样本。

时间预算通过`card_fused.max_frame_gap_seconds`配置，当前为1.0秒。
这是可调整的工程保护阈值，不是德州规则，也不是已完成真机标定的延迟指标。
重复帧号在视觉层会清空；更上层的观察顺序检查仍可拒绝非递增帧号，不会静默放宽全局顺序。

## 已知采集失败时的处理

`RealtimePipeline`在帧源抛出异常时清空视觉临时缓存和连续确认记录，保留规范牌局历史。
最新对外快照中的字段变为UNKNOWN，权益标记`capture_unavailable`；不会把旧牌/旧权益当成当前有效。
下一次输入需要重新确认，临时失败前的确认次数不能继续使用。

桌面恢复循环会使缓存策略失效；如果已经有上一帧，则在重试等待前发送无建议、不可用的快照。
通知沿用最后捕获的帧号，不伪造一张新采集帧。首次采集前尚无快照时维持原错误/健康通知逻辑。
已有UI根据快照置信度隐藏卡面和权益；本轮测试验证到生成/发送数据对象的链路，未做真实浏览器视觉验收。
WebSocket自身断线、页面挂起和视频设备内部重复陈旧像素，是与这些帧源异常不同的场景。

## 故障注入：明确不是实机故障证据

选用已经目检的源帧11340（7s/2c），保持原始像素不变，只改变输入元数据/识别路径：

| 场景 | v7基线是否要求重新积累 | v8结果 |
|---|---|---|
| 帧号跳跃 | 否 | 先拒答，积累3个新样本后接受 |
| 时间跳跃5秒 | 否 | 同上 |
| 来源标识改变 | 否 | 同上 |
| 整组底牌ROI缺失后恢复 | 恢复后立即复用旧缓存 | 恢复后重新积累 |
| 重复同一帧编号 | 继续累计 | 清空并重新积累 |
| 显式中断重置 | 原视觉层无对应入口 | 重新积累 |

6类注入用例全部通过。基线在旧v7源码快照运行，新版在当前源码运行；数据和模型哈希均保存。
反复使用同一张实拍图，不能冒充多场真实牌局或真实USB/ADB断连。
这里的3个样本是融合层门槛；生产管线另有连续确认，不承诺恢复3帧后就能给出策略。

## 正常录像没有退步

两个现有窗口重新顺序回放，使用冻结v6点数候选和rank-floor0.50：

- 10400–11500，1101帧：111个人工目检点，底牌144正确/6拒答/0错，公共牌266正确/11拒答/0错；
  无可读底牌槽位72/72、无可读公共牌槽位278/278无误报。
- 14500–17050，2551帧：原第三批8个目检点，底牌15正确/1拒答/0错，公共牌20正确/0错；空公共牌20/20。

共3652帧的逐帧轨迹与v7对应窗口逐字节相同（包括分数、字形计数和当前证据标记）。
这是回归证据，不是3652帧都有人工真值，也不是新增独立留出集。

主回放工具现在从视频容器PTS生成确定性时间，不再把机器处理耗时当成源帧间隔。
原录像容器时间与手机墙钟不同，因此PTS不能用来证明真实硬件间隔或端到端延迟；
实际长间隔行为由上面的明确元数据注入验证。
旧的静态诊断工具若不调用帧生命周期入口，不能据其结果宣称具有这些时间保护。
